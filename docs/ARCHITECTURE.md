# Architecture decision and boundaries

The audited repository is a five-product vanilla storefront deployed to GitHub Pages. There is no server, WordPress installation, database, account, approved logo asset or provider secret in the workspace. Both checkout and inventory must have one owner; this change selects WooCommerce and does not introduce a second order database.

The static site remains a price catalogue and WhatsApp quote flow. `npm run build` also packages a WordPress plugin embedding exactly the same HTML/CSS/JS through `[mvn_storefront]`. In WordPress, published SKU mappings link to native Woo product pages and inject the current authorized Woo prices. Static-mode prices are the issue’s published retail snapshot; WordPress prices are authoritative for transactions. Woo owns accounts, saved addresses, guest/customer cart, coupons, stock, taxes, checkout, orders, order emails, history, payment links, cancellation and refund records. Use classic `[woocommerce_cart]` and `[woocommerce_checkout]`; the Store API is deliberately denied until its tier isolation can be integration tested. This means Woo Blocks are **not supported** by this plugin.

Custom code owns account partner applications, admin approval/revocation, private price/MOQ fields, tier-only catalogue restrictions, server cart recalculation and non-payable quote requests stored as Woo orders. Applications use the signed-in account's WordPress email; they do not create a separate customer database. The quote shortcode currently supports one product per request; WhatsApp remains the multi-product enquiry option. Orders in `mvn-quote` status must be reviewed by staff before conversion to pending payment. Quote submissions are nonce protected and limited to one per user per five minutes. Do not interpret quote totals as final tax/shipping offers.

The initial eight SKUs are independent simple Woo products representing the issue's variants. A standalone navy template covers native Woo product/shop/cart/account/checkout and partner pages without replacing the active theme globally. This keeps each pack's stock, product image, pricing and review independent. The homepage groups these into existing variant controls. Native Woo product management supplies galleries, related products and verified product fields. Custom private fields are supported on simple products; advanced variable-product tier editing is not yet supplied. Do not switch the seeded SKUs to variable products without testing their child restrictions and cached prices.

Private prices and purchase costs are underscore-prefixed post metadata, never shipped in the static bundle. Only approved roles select private prices. Product visibility, purchasability, SQL queries, add/update cart and checkout validation enforce access/MOQs; cached variation prices vary by tier. Authenticated pages and REST responses are private/no-store. Configure the host/CDN to bypass **all authenticated, cart, account, checkout and Woo session traffic**. Never use a caching plugin that bypasses PHP for these requests. Tier prices aren't a public API. Native authenticated Woo REST administration requires privileged credentials; keep it server-side.

Razorpay and Shiprocket are intentionally delegated to their maintained WooCommerce integrations: these must write into the same Woo order, with signature/webhook verification, provider idempotency and shipment events supplied by those integrations. This repository does not implement or claim a tested provider adapter. Select and verify exact vendor plugin versions in staging before checkout enablement. Never accept a browser success callback as proof of payment. GST invoice generation must be handled by one selected accounting integration after accountant review; Woo order numbers alone are not asserted to be GST invoice numbers.

Checkout is blocked by default, including pay-for-order, until `mvn_checkout_enabled=yes`. Every seeded product also has a private review hold. This is a deployment safeguard, not an assertion that toggling the option certifies readiness. No real payments or production deployment are authorized by this PR.
